# ADR-001: JWT with Local Secret and Claims vs OAuth

## Status
Accepted — JWT with local secret and claims will be used for the demo submission. In production, this will be replaced by OAuth2/OpenID Connect with a managed identity provider.

## Context
The MLOps demo platform requires role‑based authorization and environment promotion controls. In production, this would typically be handled by an identity provider (e.g., OAuth2, OpenID Connect, Azure AD). However, for this assignment:

No external authentication service is available.

The submission must be self‑contained and runnable via Docker Compose.

Governance requirements (approval workflow, promotion safety, rollback controls) must still be demonstrated.

## Decision
We will use JWTs signed with a local secret key to encode authorization claims.
Each token includes:

role → Defines user capability (admin, approver, operator, guest).

env → Deployment environment (staging, production).

exp → Expiry timestamp to prevent replay or stale tokens.

The backend (FastAPI) verifies the JWT signature using the shared secret and enforces governance rules based on claims.

## Alternatives Considered
 - A combination of hmac.new and hashlib.sha256 was considered to compare the digest. But was rejected considering jwt automatically checks standard claims such as expiration time (exp) and audience. jwt also support asymmetric algorithms such as RS256 (RSA using SHA-256) and will be easier to integrate with production ready auth providers like Okta.
 - Plain strings in headers was considered. But since its Too simplistic, no integrity protection, easy to spoof hence, Rejected because it fails governance and audit expectations.

## Consequences
### Positive

 - Standard JWT format recognizable to reviewers.
 - Demonstrates expiry, environment, and role claims.
 - No external infra required — fully self‑contained demo.
 - Extensible: can add tenant_id, iat, aud claims later.
 - Easy migration path to OAuth/JWT provider in production.

### Negative

 - Shared secret must be distributed to frontend, which is insecure in real deployments.
 - No user identity management (only role/env claims).
 - No refresh tokens or revocation mechanism.
 - Not suitable for multi‑tenant production without an identity provider.


## Follow-up Actions
**Secret Management**
 - Move the local `SECRET_KEY` into environment variables or Docker secrets.  
 - Document rotation procedure for production.

**Token Issuance**
 - In production, integrate with an identity provider (OAuth2/OpenID Connect).

**Claim Expansion**
 - Add `tenant_id` for multi‑tenancy.  
 - Add `iat` (issued at) and `aud` (audience) claims for stricter validation.

**Governance Enforcement** 
 - Add audit logging of claim checks for traceability.


**Future Migration Path**  
 - Document how to swap local JWT signing for OAuth provider integration.  
 - Identify risks and mitigation steps for migration (e.g., token revocation, refresh flows).
